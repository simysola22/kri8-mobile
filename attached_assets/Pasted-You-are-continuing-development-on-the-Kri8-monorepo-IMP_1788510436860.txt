## 1. GET INSPIRED / AI FIX

Problem observed in the APK:

The "Get Inspired" feature produced shallow, low-quality results. For example, entering:

`house hunting`

could produce something like:

`The psychology of house — why it works better than you think`

This is unacceptable because "house hunting" is a complete concept, not merely the keyword "house".

The previous audit found this pipeline:

```text
Mobile AI screen
  app/(tabs)/ai.tsx
    ↓
useGetInspiration()
  src/hooks/useTrends.ts
    ↓
POST /api/trends/inspire
    ↓
artifacts/api-server/src/routes/trends.ts
    ↓
createTrendProvider()
provider.getKeywordTrends([title])
    ↓
generateInspiration(title, notes, keywordTrends)
  lib/trend-engine/src/inspiration.ts
    ↓
OpenAI request OR template fallback
    ↓
Results rendered in ai.tsx
```

The phrase could be weakened by keyword tokenization.

Approved requirements:

* Preserve the complete user title/concept.
* Multi-word concepts must be treated as semantic phrases.
* Improve the OpenAI prompt substantially.
* Generate useful, specific, differentiated creator ideas.
* Avoid generic first-word keyword output.
* Do not expose or request chain-of-thought.
* Return only the required structured output from the model.
* If OpenAI is genuinely unavailable, template fallback may remain.
* The client must be able to tell whether results came from OpenAI or templates.
* Do not silently disguise template output as AI output.
* Configured OpenAI failures should remain real failures, not silently become fake successful template responses.

The approved conceptual change was:

```ts
export interface InspirationResult {
  relatedIdeas: string[];
  alternativeHooks: string[];
  titleSuggestions: string[];
  audienceQuestions: string[];
  source: "openai" | "template";
}
```

The OpenAI prompt should explicitly instruct the model to:

* use the complete title as the primary subject
* preserve multi-word concepts as phrases
* infer audience intent
* infer creator goal where useful
* consider platform/content fit
* create differentiated angles
* make suggestions actionable and creator-specific
* avoid generic trend commentary

The template fallback should prioritize:

```ts
title.trim()
```

over reconstructed tokenized keywords.

Example principle:

```ts
const keyword =
  title.trim() ||
  primaryKeywords.slice(0, 6).join(" ") ||
  "content";
```

Successful OpenAI output should be returned as:

```ts
{ ...aiResult, source: "openai" }
```

Template output should be returned as:

```ts
{
  relatedIdeas,
  alternativeHooks,
  titleSuggestions,
  audienceQuestions,
  source: "template",
}
```

Likely files:

* `lib/trend-engine/src/inspiration.ts`
* `lib/trend-engine/src/types.ts` if the type is defined there
* `lib/api-spec/openapi.yaml`
* generated API/Zod/client contract files
* `artifacts/kri8-mobile/src/types/api.ts`
* `artifacts/kri8-mobile/src/services/AIAssistantService.ts`
* `artifacts/kri8-mobile/app/(tabs)/ai.tsx`

Generated API contracts must come from the canonical OpenAPI schema where possible. Do not manually create divergent contracts.

For rollout compatibility, the mobile `source` field may be optional if necessary while an older deployed backend still exists:

```ts
source?: "openai" | "template";
```

# 3. SOCIAL SECURITY FIX

The previous audit found an important backend authorization issue.

`GET /api/social/messages/:userId` authenticated the caller but did not verify that the requested partner was an accepted friend.

The POST route already required an accepted friendship.

The GET route must enforce equivalent authorization before returning conversation history.

Requirements:

* Reject invalid numeric IDs.
* Reject self-conversations through this route where appropriate.
* Verify an accepted friendship exists between the authenticated user and the requested partner.
* Return `403` if they are not accepted friends.
* Preserve existing valid messaging functionality.
* Do not weaken existing authorization.
